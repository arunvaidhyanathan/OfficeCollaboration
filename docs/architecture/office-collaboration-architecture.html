1. Requirements recap

A React + TypeScript SPA where a user can initiate a new document or upload an existing one (docx/xlsx/pptx/pdf), see it in a document list, and open it for co-authoring in-page via the embedded ONLYOFFICE editor (not a redirect). Java/Spring Boot ("Document Core") owns auth, document/version metadata, and ONLYOFFICE's save callback. Documents live in S3, never in Postgres. Postgres is your existing Supabase project. nginx fronts everything. AI/Parsing is a real, named part of the target architecture but is explicitly deferred past this POC.

2. ADR-001 — Monolithic SPA vs. Micro-Frontends

Do we build the React UI as Micro-Frontends?Decision: NOT YET

Context

MFE (independently built and deployed frontend bundles composed at runtime) solves an organizational problem — multiple teams needing to ship on independent schedules without a shared release train — not a technical one. Your app has two logical surfaces (a document/workspace shell, and the ONLYOFFICE editor iframe) and, based on what you've described, one team building it. The editor itself is already isolated: ONLYOFFICE's React integration mounts the editor as its own component/iframe with its own JS runtime, so you get most of MFE's isolation benefit (independent failure domain, independent update cadence for the editor vs. your shell) for free, without adopting MFE machinery for the rest of the app.

Options considered

OptionProsCons
A. Single SPA (recommended) — one Vite/CRA-equivalent React+TS build, internally modularized by domain (/documents, /workspace, /ai-search, /admin) with route-based React.lazy code-splittingSimplest CI/CD (one pipeline); one dependency tree, one design system instance, no version-skew between "micro" apps; smallest bundle-orchestration risk; fastest to buildAll feature teams share one deploy train and one React/router/build-tool version until you outgrow it
B. Micro-frontends now (Module Federation)Independent deploys per domain; teams can pick different release cadencesReal, non-trivial cost: shared-dependency version negotiation, shared design-system contract, cross-remote error boundaries, harder E2E testing, slower initial build — paid up front for a problem (multi-team independence) you don't have yet
C. iframe-per-tool compositionMaximum isolationLoses SPA-level state sharing, deep-linking, and shared auth context; you'd be fighting the framework to get the "feels like one app" experience item 12 of your own brief asks for
DecisionBuild Option A. Structure the codebase as if it might federate later — domain-based folders under src/domains/<name>, no cross-domain imports except through a shared @app/ui-kit and @app/api-client package, each domain lazy-loaded at the router level. This is the standard "modular monolith" precursor to MFE: if a domain later needs to become an independently-deployed remote, the extraction is a build-config change, not a rewrite, because the domain already has no illegal imports into siblings.

Revisit when

You have ≥2 teams that need to ship independently, or a specific domain (e.g. the AI/search surface) needs a materially different release cadence or even a different framework. At that point, go to ADR-002.

7. Corrected sequence flows

7.1 Opening a document for (co-)editing — as built

  1. React calls GET /api/v1/documents/{id}/editor-config. In the current MVP there is no session token to send — the call runs as the fixed LocalUser (§0.2); when real auth is restored this is where the Supabase session token goes back in.
  2. Document Core checks document_permissions for that (document, user) pair (the ACL check runs for real; it's just always the same user for now).
  3. Document Core sets document.url in the config to its own GET /api/v1/onlyoffice/content?documentId=..., not a presigned S3 URL — see §8.7 for why the presigned-URL approach originally planned here doesn't work with ONLYOFFICE.
  4. Document Core builds the ONLYOFFICE config object with a stable, content-derived key (documentId + "_" + versionId, generated once per version — the fix for §8.1's bug) and signs it with the Document Server's shared secret.
  5. React mounts <DocumentEditor> (the official @onlyoffice/document-editor-react package) with that config; ONLYOFFICE Document Server calls back into Document Core's content endpoint to fetch the file and opens/joins the co-authoring session for that key.

7.2 Saving (the callback)

  1. ONLYOFFICE's internal co-authoring service handles keystroke-level sync between connected clients — this never touches your backend.
  2. On "everyone closed the doc" or forced save, Document Server POSTs to your callbackUrl with status and a one-time url to fetch the resulting file, signed with a JWT in the Authorization header.
  3. Document Core must validate that JWT (shared secret, same one configured on the Document Server) before trusting the payload — your pasted CallbackController does not do this; see §8.2.
  4. Document Core downloads the file from the Document-Server-provided URL over the internal network, uploads it to S3 as a new version, updates document_versions/documents.current_version_id — synchronously, in the callback response. No queue, no outbox, for the POC (confirmed §0.1).

7.3 RAG ingestion Phase 2 — not built

Deferred. When AI/Parsing is built, this is the seam: Document Core's save-callback (step 5 above) is where a Phase-2 event to the Python service would be emitted — decide then whether that's a direct call, a Postgres outbox, or your org's existing broker (ADR-003 watch item).

7.4 Presence — "who's viewing/editing this document" Not built

Confirmed to live in the UI shell (§0.1 item 9), not as a Postgres table — but as of this review, no presence code exists in the frontend at all (§0.2). Recommended approach, unchanged from the original plan: a Supabase Realtime Presence channel keyed by document id — each open editor tab tracks itself on presence:document:<id> with its user id, and every client subscribed to that channel gets the live roster for free, with no backend code and no table to clean up on disconnect (Realtime handles leave-detection). This depends on real per-user identity existing first (§0.2's auth deviation) — with everyone currently the same LocalUser, a presence roster wouldn't show anything meaningful yet anyway, which is likely why it was skipped for this pass.

8. Line-by-line review of your pasted blueprint

Your architecture diagrams and table designs are kept as-is below except where noted — most of the blueprint is right. These are the specific defects worth fixing before you build from it.

8.1 Fix The ONLYOFFICE document key is generated wrong

Your DocumentService.java does:

documentObj.put("key", docId + "_" + System.currentTimeMillis());

ONLYOFFICE uses key to identify a co-authoring session for a specific document version — the Document Server caches state per key and expects the same key to be reused by every user opening the same version, so they land in the same session. Minting a new key from currentTimeMillis() on every editor-config request means two users opening "the same document" thirty seconds apart get two different keys, i.e. two separate, non-collaborating sessions — this silently breaks the co-editing requirement that is the whole point of the project. Fix: derive key deterministically from something that only changes when the underlying file changes, e.g. docId + "_" + currentVersionId or a content checksum, generated once when a new version is stored, not on every config request.

8.2 Fix — security The callback controller doesn't validate the incoming JWT

Your CallbackController.handleOnlyOfficeCallback reads status and url straight off the request body with no signature check. ONLYOFFICE signs this callback with the shared secret precisely so your endpoint can tell "this really came from our Document Server" apart from "anyone who can reach this URL." As written, any caller who can reach /api/v1/documents/callback can pass status: 2 and a URL of their choosing and your service will fetch and persist whatever that URL returns as the new authoritative document version. Fix: validate the Authorization (or body-embedded, per your config) JWT against the same secret configured via JWT_SECRET/local.json on the Document Server side, and reject unsigned/invalid requests before touching S3.

8.3 Fix Don't hand ONLYOFFICE a permanent public S3 URL

Your sample document.url is a bare s3DownloadUrl. If that's a long-lived public or long-TTL signed URL, anyone who obtains it (logs, browser history, a shared link) can fetch the file outside your ACL checks. Generate a short-TTL presigned URL at editor-config time, scoped to that one request.

8.7 New finding Presigned S3 URLs don't work as ONLYOFFICE's document.url — found and fixed during the build

§8.3 above recommended a short-TTL presigned S3 GET URL for document.url in the editor config, instead of a permanent public URL — correct in isolation, but it turns out to still be the wrong mechanism for this specific caller. ONLYOFFICE Document Server attaches its own Authorization: Bearer <jwt> header to every outbound HTTP request it makes, including the one it makes to go fetch document.url. A presigned S3 URL authenticates via query-string parameters (SigV4) — when ONLYOFFICE's extra Authorization header rides along on top of that, S3 sees a request with two conflicting auth mechanisms and rejects it with 400 Bad Request, before the document ever loads.

The fix actually shipped: document.url now points at a new endpoint on Document Core itself, GET /api/v1/onlyoffice/content?documentId=... (OnlyOfficeCallbackController#content), which downloads the object from S3 server-side (S3StorageService.download, plain GetObject, no presigning) and streams the bytes back. ONLYOFFICE's extra header is simply ignored by that endpoint — Document Core doesn't require it for authentication (§0.2 — there's no per-user auth at all yet), so there's no conflict to have. S3StorageService.presignedGetUrl(...) is still in the codebase but nothing calls it anymore; safe to delete next time you're in that file.

Watch — once real auth comes backWhen §0.2's auth deviation is fixed and this endpoint needs to check that the caller actually has access to the document (right now it does — it calls documentService.loadForEditorConfig, the same ACL check as everywhere else, keyed on the fixed LocalUser), keep in mind ONLYOFFICE is the caller here, not the end user's browser — it cannot forward a Supabase session token it never had. Continue verifying this specific endpoint via the ONLYOFFICE-side shared secret (as the callback endpoint already does, §8.2's fix), not via a per-user token, or document loads will break.
